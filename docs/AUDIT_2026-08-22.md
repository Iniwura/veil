# VEIL Code, Integration, and Demo Audit — 22 August 2026

## Scope

This audit reviewed the current VEIL competition build end to end:

- `VeilPool.sol`
- `VeilYieldSource.sol`
- `VeilPrizeVault.sol`
- `MockConfidentialToken.sol`
- deployment configuration and scripts
- Sepolia smoke flow
- React/Vite frontend
- wallet/provider handling
- Zama Relayer SDK integration
- CI workflows
- Hardhat tests and coverage
- submission documentation and repository hygiene

This is an internal engineering audit for a testnet competition build. It is not an independent professional security audit.

## Executive summary

The core FHE custody, ACL, snapshot, winner-proof, yield, and prize flows are substantially better tested than the browser integration. The protocol test suite currently covers operator authorization, actual transferred-value accounting, user-only decryption, snapshot immutability, 32-player capacity, BlindDraw, public winner proof verification, confidential yield allocation, winner-only prize decryption, and confidential prize claim.

The main source of live failures has been the browser boundary: injected-wallet selection, relayer initialization, wallet transaction timing, public reads through injected providers, and frontend state assumptions. Existing CI builds the frontend but does not execute wallet/relayer/browser transaction flows.

The audit also found protocol-level liveness and capacity limitations in the deployed pool. Those cannot be corrected in source while still claiming that the current repository exactly represents the already-proven Sepolia deployment. They require a deliberate contract revision and new deployment, or must remain documented testnet limitations.

## Confirmed findings

### V-01 — Unsafe live-network mnemonic fallback

**Severity: High**

The Hardhat configuration previously used the standard public development mnemonic as the fallback for every configured network, including Sepolia. If a developer forgot to configure `MNEMONIC`, a live command could derive publicly known accounts.

**Fix:** Sepolia now receives no configured accounts unless an explicit Hardhat `MNEMONIC` is present. The standard test mnemonic remains available only for local Hardhat/Anvil development. The default Sepolia RPC is now the public Sepolia endpoint already used by the frontend.

### V-02 — False faucet prerequisite blocked funded wallets

**Severity: High for demo reliability**

The frontend used `dashboard.joined` as a proxy for whether a wallet owned demo cUSD:

```text
joined === false -> demoFunded === false -> deposit disabled until faucet succeeds
```

Those concepts are unrelated. A wallet can own confidential demo tokens without having joined VEIL. This was directly visible with the Sepolia deployer wallet, which the successful smoke script had already funded but which the UI still treated as unfunded because it had not joined the pool.

**Fix:** the faucet is now optional convenience. A connected wallet can always attempt a positive deposit. Existing funded wallets no longer need a new mint transaction.

### V-03 — Injected-wallet provider was overloaded with unrelated responsibilities

**Severity: Medium**

Earlier frontend versions used the injected provider for public dashboard reads and relayer networking as well as signing. Multiple wallet extensions can compete for `window.ethereum`, making harmless reads and FHE networking depend on browser-extension injection state.

**Fixes applied:**

- public dashboard reads use a dedicated Sepolia `JsonRpcProvider`;
- public operator checks also use the dedicated RPC;
- Zama Relayer SDK networking now uses the stable Sepolia RPC URL;
- injected provider is kept for wallet account access, signatures, and transactions;
- when an injected provider list exists, VEIL prefers the MetaMask provider.

### V-04 — Unbounded pending promises produced frozen UI

**Severity: Medium**

Wallet requests, transaction submission, receipt waits, encryption, and decryption could remain pending indefinitely. This caused the UI to remain at `FUNDING...` without a new application error.

**Fix:** bounded waits now wrap wallet connection, faucet minting, pool authorization, deposit, withdrawal, FHE encryption, private decryption, and receipt confirmation. Timeouts are cleared when operations settle.

### V-05 — Raw provider/ethers failures were unsuitable for product UI

**Severity: Low-Medium**

Earlier builds exposed raw `CALL_EXCEPTION` details in Activity. Later sanitization became too generic to debug.

**Fix:** the UI remains concise, while the real stage-specific error is logged to DevTools with a `[VEIL]` prefix. Deposit, withdrawal, funding, operator authorization, and encryption have separate error classes.

## Protocol findings requiring a new deployment to fully fix

### V-06 — Permanent membership-slot exhaustion

**Severity: High**

`playerCount` only increases. Once an address joins, withdrawing its full principal does not remove it from `players`, clear `joined`, or reclaim its array slot.

Consequences:

- after 32 addresses have ever joined, new participants cannot enter;
- zero-balance historical participants remain in every future snapshot;
- the 32-player boundary is therefore a lifetime-registration boundary, not a concurrent-active-user boundary.

**Recommended revision:** implement explicit active membership lifecycle, or use a round-specific participant registry that only includes accounts with eligible positive principal. Any removal design must preserve historical snapshot immutability.

### V-07 — Zero-value registration / zero-total draw liveness failure

**Severity: High**

`deposit()` registers a new address after the confidential transfer even if the actual transferred value is zero. A participant can also withdraw its full balance and remain registered.

`snapshotRound()` checks only `playerCount >= 2`; it does not prove that the encrypted total weight is positive. If all included weights are zero:

1. `blindDraw()` never crosses a positive cumulative weight;
2. encrypted winner remains the zero address;
3. public decryption yields zero;
4. `finalizeWinner()` rejects zero with `No eligible winner`;
5. the round remains stuck in `DRAWN`.

This is a real liveness/DoS condition in the deployed design.

**Recommended revision:** prevent zero-value initial registration and define an explicit eligible-active participant rule. A future draw design should also have a recoverable state transition if no eligible winner exists.

### V-08 — No explicit `euint64` economic bound

**Severity: Medium-High**

Principal balances, snapshot weights, total weight, unallocated yield, and prizes use encrypted `uint64` arithmetic. The protocol does not enforce an application-level maximum total principal/weight that guarantees additions cannot wrap.

The test-only token's unrestricted mint makes adversarial testnet overflow especially easy to attempt.

**Recommended revision:** define and enforce maximum per-position and aggregate economic bounds compatible with `uint64`, or move critical aggregate arithmetic to a wider encrypted type where appropriate.

### V-09 — Owner-controlled round progression

**Severity: Informational / trust assumption**

`snapshotRound()` and `blindDraw()` are owner-only. Winner finalization is permissionless once the public decryption proof exists, but the owner controls when snapshots and draws occur.

This is acceptable for the competition prototype if documented, but it is a protocol-centralization/liveness assumption for production.

### V-10 — Yield allocation does not validate round lifecycle

**Severity: Medium operational risk**

`VeilYieldSource.allocateToRound(roundId, ...)` is owner-only and can allocate to any numeric round ID. It does not check that the round exists or is finalized. The prize vault later prevents winner authorization until `pool.getWinner(roundId)` succeeds, so external theft is not introduced, but an operator can strand/misroute prize accounting.

The README language saying yield is allocated to a finalized round is therefore stronger than the contract invariant.

**Recommended revision:** add a round-state interface check before allocation, or correct documentation and operational procedures.

## Demo asset and economic-model findings

### V-11 — Unrestricted test-token minting

**Severity: Medium for public demo integrity; intentional test behavior**

`MockConfidentialToken.mint()` is permissionless. This is clearly labeled as test-only in source and deployment docs, but any Sepolia user can mint arbitrary demo balances and influence future pool weights if the pool remains publicly usable.

This must never be described as a production asset or production anti-Sybil/economic model.

The optional frontend faucet is convenience only; it is not a security boundary.

### V-12 — Trusted asset semantics

**Severity: Low-Medium architecture assumption**

Pool, yield source, and prize vault trust the immutable configured confidential asset to return a correctly bounded `transferred` ciphertext and to follow expected transfer semantics. The demo asset does this. Deployment with an arbitrary external asset address does not currently validate those semantics beyond successful calls.

Production integration should whitelist/audit the exact asset implementation.

## Frontend and browser findings

### V-13 — No browser transaction test coverage

**Severity: Medium**

Current CI verifies TypeScript compilation and Vite production build, but it does not execute:

- wallet connection;
- chain switching;
- provider selection;
- relayer initialization;
- encrypted input creation;
- operator authorization;
- deposit/withdraw transactions;
- user decryption;
- account or chain changes;
- mobile action/error visibility.

Every live issue encountered during final QA was in this untested boundary.

**Recommended hardening:** add unit tests around a provider adapter/state machine and a small Playwright-style browser test with mocked EIP-1193 provider. Live Sepolia smoke should remain a separate manual/credentialed check.

### V-14 — Frontend excluded from root ESLint

**Severity: Medium engineering quality**

The root ESLint configuration explicitly ignores `frontend/**`. The frontend workflow currently runs only `tsc` and Vite build. A green root `lint` therefore does not lint React/frontend code.

**Recommended hardening:** add a frontend ESLint configuration/script and run it in frontend CI.

### V-15 — Frontend install is non-deterministic

**Severity: Medium supply-chain/reproducibility**

The frontend directory has no committed `package-lock.json`; its CI uses `npm install`, so the exact transitive dependency graph can drift between runs.

**Recommended hardening:** commit a frontend lockfile and use `npm ci`.

### V-16 — Wallet account/chain changes can stale local UI state

**Severity: Medium UX/integration**

The app currently establishes signer/address/dashboard state at connect time but does not subscribe to injected-provider `accountsChanged` and `chainChanged` events. A user can change account/network in the wallet and leave VEIL showing stale state until reconnect/reload.

**Recommended hardening:** add a small wallet session adapter that resets or refreshes signer state on these events.

### V-17 — No application error boundary

**Severity: Low-Medium UX reliability**

A previous bad Relayer SDK import caused a complete white screen because the app has no React error boundary/fatal fallback.

**Recommended hardening:** render a minimal VEIL recovery screen with reload/debug guidance for uncaught render/runtime failures.

### V-18 — Activity/errors disappeared below 1100 px

**Severity: Low UX**

Base responsive CSS hid `.right-rail`, which contains Activity and error feedback, on tablet/mobile.

**Fix:** final polish now reintroduces the Activity/prize/proof rail as a full-width section below the main dashboard on smaller screens.

### V-19 — Disabled controls used a waiting cursor

**Severity: Low UX**

Base CSS applied `cursor: wait` to every disabled button, including controls disabled for permanent state reasons such as withdrawal before joining.

**Fix:** final polish changes disabled controls to `not-allowed`.

### V-20 — Landing “How it works” did not reach protocol section

**Severity: Low UX**

The landing view linked to `#protocol`, but the protocol section only exists after entering the dashboard view.

**Fix:** the action now enters the app and scrolls to the protocol section after render.

## CI, dependency, and repository findings

### V-21 — Dependency audit currently reports known vulnerabilities

**Severity: Requires dependency-level triage**

The latest root CI install reports:

- 18 low
- 12 moderate
- 25 high
- 1 critical

These counts are not enough to determine exploitability in VEIL because many dependencies are development tooling/transitive packages. They should not be dismissed, and `npm audit fix --force` should not be applied blindly because it can introduce breaking dependency changes.

**Recommended hardening:** capture `npm audit --json`, classify runtime vs dev-only findings, update safe direct dependencies, and document any accepted transitive toolchain risk.

### V-22 — No coverage thresholds

**Severity: Low-Medium engineering quality**

Solidity coverage is generated but CI does not enforce minimum line/branch/function thresholds. A future regression could reduce coverage without failing CI.

### V-23 — Stale Zama template artifacts remain

**Severity: Low-Medium submission/repository quality**

The repository still includes:

- `contracts/FHECounter.sol`
- `tasks/FHECounter.ts`
- `test/FHECounter.ts`
- `test/FHECounterSepolia.ts`
- Hardhat config import for the template counter task

The Sepolia counter test is the permanent `1 pending` result in otherwise clean VEIL test output.

**Recommended cleanup:** remove template-only artifacts after VEIL functionality is locked.

### V-24 — Root package metadata still identifies the template

**Severity: Low submission quality**

The root `package.json` and lockfile still use the package name/description/homepage/repository metadata of `fhevm-hardhat-template` rather than VEIL.

**Recommended cleanup:** rename package metadata to VEIL and regenerate the lockfile without changing dependency versions unnecessarily.

### V-25 — Deployment migration ID needs deliberate versioning

**Severity: Low-Medium deployment operations**

The deploy script still uses `func.id = "deploy_veil_v1"` while contract comments and behavior have progressed through later prototype revisions. Hardhat Deploy uses IDs to decide whether migrations already ran.

Any future contract revision/redeploy should use a new deployment ID deliberately rather than silently editing an already-applied deployment step.

## Areas that tested well

The audit did not find a cross-user balance decryption path in the current test architecture. Existing tests explicitly reject Alice decrypting Bob's balance and vice versa.

The following properties are covered well in local FHEVM tests:

- pool must be authorized as confidential-token operator;
- pool credits only the amount the asset actually transfers;
- deposits for different users remain separate;
- withdrawals clip to available confidential principal;
- historical snapshots stay immutable while live positions change;
- users decrypt only their own historical snapshot weight;
- 32-player capacity is enforced as currently designed;
- BlindDraw can run only once per snapshotted round;
- invalid public winner proofs are rejected;
- winner finalization is permissionless after valid proof;
- prize accounting is separate from principal;
- direct unauthorized prize credits are rejected;
- only the finalized winner can decrypt and claim a prize;
- losing participants cannot claim;
- yield/prize accounting clips to real confidential assets.

The successful Sepolia smoke run additionally proves that one complete deployed path worked from mint/operator/deposit through private balance decrypt, snapshot, BlindDraw, public winner proof, confidential yield, prize authorization, winner-only decryption, and claim.

## Submission guidance

For the current Season 4 submission, keep claims scoped to what has actually been demonstrated:

- testnet competition prototype;
- FHE-backed confidential principal and weighted selection;
- publicly verifiable finalized winner;
- confidential prize ACL/claim flow;
- test-only mock asset on Sepolia;
- public wallet/transaction metadata;
- owner-controlled snapshot/draw progression;
- no claim of production readiness or independent security audit.

Do not imply that the current 32-player deployment supports indefinite participant churn or that zero-weight draw liveness is solved. Those require the next contract revision.
