## Fixed protocol findings

### V-06 — Bounded reusable draw seats

The original pool treated its 32-player array as permanent lifetime registration. A sufficiently large set of historical
addresses could therefore exhaust future participation.

The final pool separates persistent confidential principal from temporary draw eligibility. Draw seats use a one-day
renewable lease. Users can renew or release a draw seat without changing principal, and expired seats can be pruned
while the underlying user position remains withdrawable and privately revealable.

This changes the 32-player limit from a permanent lifetime-registration limit into a bounded active draw roster.

A remaining testnet limitation is temporary Sybil seat spam: an attacker can still occupy multiple active seats for the
duration of the lease. Production use would need an anti-Sybil or economic admission policy.

### V-07 — Recoverable all-zero draws

The original design could enter `DRAWN` with an encrypted zero-address winner when every snapshotted weight was zero,
after which winner finalization could not complete.

The final design adds `DrawState.CANCELLED`. A valid KMS public decryption proving a zero winner now transitions an
all-zero draw to `CANCELLED` rather than leaving it stuck.

The test suite includes a dedicated all-zero cancellation regression.

### V-10 — Prize/yield lifecycle validation

Prize funding is now tied to a finalized winner. `VeilPrizeVault.recordPrize` validates the finalized round winner
through the pool before recording the prize. Attempts to allocate before winner finalization revert atomically rather
than stranding confidential prize accounting.

Yield allocation also follows all-or-zero confidential semantics: an oversized encrypted allocation request selects zero
instead of clamping to the remaining realized yield.

Principal custody, realized-yield custody, and prize custody remain separated.

### V-26 — Pooled-custody oversized withdrawal

A browser regression uncovered a high-impact pooled-custody bug in an earlier hardened deployment.

A user with `1` unit of private VEIL principal requested a withdrawal of `2`. The asset contract checked the encrypted
request against the pool’s aggregate token balance, which included other depositors’ assets. Because the pool held
enough aggregate custody, the token transferred `2`; the pool then subtracted `2` from the caller’s encrypted position
of `1`, producing encrypted `uint64` wraparound.

The final `VeilPool.withdraw` first derives an encrypted `permitted` amount from the caller’s own private position:

- request within caller principal → requested amount is permitted;
- request above caller principal → encrypted zero is permitted.

Only that permitted ciphertext is transiently authorized to the confidential asset. This prevents another participant’s
pooled custody from satisfying an oversized caller request.

Regression coverage includes a multi-depositor case where Alice has `1`, Bob has `20`, and Alice requests `2`. Alice
remains at `1`, Bob remains at `20`, and no other depositor custody is spent.

The final Sepolia browser check repeated the exact exploit path: deposit `1`, reveal `1`, request withdrawal `2`, reveal
remains `1`.

## Privacy and trust model

VEIL keeps the following values confidential through FHE:

- user principal balances;
- deposit and withdrawal amounts at the application-value layer;
- draw weights;
- snapshot weights;
- prize amount before authorized winner decryption.

The following metadata remains public:

- participant addresses;
- transaction occurrence and timing;
- draw-seat membership;
- round lifecycle;
- finalized winner identity;
- prize authorization/claim state.

Exact private balances are not inferred by the frontend. A user sees plaintext only after an explicit wallet-scoped
Reveal operation.

In the current source, snapshot and BlindDraw progression are permissionless after the fixed scheduled close time and
valid round-state checks. Winner finalization remains permissionless once a valid KMS public decryption proof is
available. The live Sepolia deployment documented above predates this change and has not been redeployed as part of this
review.

## Demo-only economic components

`MockConfidentialToken` is intentionally test-only and supports permissionless minting. It must not be described as a
production asset or production anti-Sybil model.

`VeilYieldSource` demonstrates asset-backed confidential yield plumbing for the competition flow. It is not a production
yield venue. A production implementation would need a reviewed confidential asset and a real yield adapter with explicit
economic and authorization constraints.

## Remaining hardening items

### Explicit encrypted arithmetic bounds

The protocol uses `euint64` for principal, aggregate weight, yield, and prize accounting. Competition values are far
below the type limit, but the protocol does not enforce a formal maximum per-position or aggregate bound that proves
encrypted additions cannot overflow.

Production work should define explicit economic bounds or use wider encrypted arithmetic for critical aggregates.

### Automated browser E2E coverage

The final browser flow was manually proven against Sepolia, but CI does not yet execute a complete injected-wallet +
relayer + encryption + transaction + decryption workflow.

A future hardening pass should add a mocked EIP-1193 browser suite and keep the credentialed Sepolia smoke as a separate
integration check.

### Frontend lint and fatal fallback

The frontend production build is verified, but root ESLint still excludes `frontend/**`. A dedicated React/TypeScript
lint configuration would improve coverage.

The app also lacks a top-level React error boundary for unexpected render/runtime failures.

### Wallet session changes

Account or chain changes in an injected wallet can still require reconnect/reload to guarantee that every cached
signer/dashboard value is refreshed. A dedicated wallet-session adapter should subscribe to `accountsChanged` and
`chainChanged`.

### Coverage thresholds

Coverage is generated in CI, but minimum coverage percentages are not enforced as hard gates.

### Future deployment migration IDs

Any later contract revision should use a new Hardhat Deploy migration ID instead of silently reusing an already-applied
deployment step.
